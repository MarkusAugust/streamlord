The browser lowercases attribute names, so a capital letter in a key never reaches Datastar: data-signals:fooBar declares $foobar. The quick fix writes the kebab-case key that comes back as the intended name, with __case.camel where Datastar's default is not camel.

In the DSL the SDK writes a camelCase key correctly on its own; a hint on the call says what goes on the wire, so nothing is hidden. A key the SDK refuses at runtime is an error instead: one holding __, where Datastar starts reading modifiers, or one ending in _ before a modifier the call adds, such as dataSignals("foo_", "1", ifMissing = true), which the client would read as foo. So is a key with whitespace, a quote or a character that ends an attribute, and a signal name no $ reaches, such as a:b, über or constructor, in a key, a pair or the name dataBind, dataRef or dataIndicator writes in the value.

A signal name in a DSL call holds no hyphen: Datastar's client reads one as a capital in an attribute key and as a hyphen in an expression or a patch, so dataSignals("foo-bar", ...) and signal("foo-bar") would name two signals, and the SDK refuses the name at runtime. The quick fix writes it in camelCase, fooBar. A key with a hyphen inside a value is data, and an expression reaches it with brackets: signal("form['first-name']").

The key of dataAttr and dataAnimate is an attribute's name as HTML has it, and the SDK refuses a capital in it at runtime: dataAttr("viewBox", ...) could only set view-box. The quick fix writes the kebab-case name, aria-label for ariaLabel; an attribute that really has capitals, such as SVG's viewBox, takes the object form, dataAttr("{viewBox: ...}").
